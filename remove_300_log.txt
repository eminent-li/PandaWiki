PandaWiki 去除 300 文档/节点限制修改与部署记录
生成时间: 2026-06-05
仓库路径: C:\D\WIP\pandawiki\PandaWiki

============================================================
一、背景与目标
============================================================

目标:
1. 分析 PandaWiki 开源版为什么只有 300 个文件/文档限制。
2. 给出最小改动方案，去除该限制。
3. 在本地修改代码并验证。
4. 将修改推送到 GitHub fork。
5. 在已部署 PandaWiki 的主机上，使用修改后的版本替换官方镜像，取消 300 限制。

用户 fork 仓库:
https://github.com/eminent-li/PandaWiki.git


============================================================
二、代码分析结论
============================================================

结论:
PandaWiki 开源版“300 个文件”限制不是 Git 同步、数据库、RAG 或向量库的自然上限，而是代码里显式写死的授权限制。

关键发现:

1. 前端展示层定义开源版每个 Wiki 文档数为 300
文件:
web/admin/src/constant/version.ts

原始关键配置:
  docCountPerWiki: 300

2. 后端默认授权限制把 MaxNode 写成 300
文件:
backend/domain/license.go

原始关键配置:
  MaxNode: 300

3. 创建节点时后端把 MaxNode 注入请求并在仓储层做硬拦截
文件:
backend/handler/v1/node.go
  req.MaxNode = domain.GetBaseEditionLimitation(ctx).MaxNode

文件:
backend/repo/pg/node.go
  if count >= int64(req.MaxNode) {
      return domain.ErrMaxNodeLimitReached
  }

4. 限制统计的是节点总数，不只是“上传文件数”
文件:
backend/domain/node.go

NodeType 包括:
  NodeTypeFolder = 1
  NodeTypeDocument = 2

仓储层计数只按 kb_id 统计，不区分类型，所以文件夹和文档都占额度。

5. 更深一层原因
文件:
backend/domain/license.go

GetBaseEditionLimitation() 会从 context 中读取 edition_limitation，
但仓库中没有任何地方把 ContextKeyEditionLimitation 写入 context，
所以实际运行时总是回落到默认值:

  MaxKb: 1
  MaxAdmin: 1
  MaxNode: 300


============================================================
三、最小改动方案
============================================================

采用方案:
1. 将 MaxNode 默认值从 300 改为 0。
2. 约定 MaxNode <= 0 表示不限。
3. 仓储层仅在 MaxNode > 0 时执行数量限制。
4. 前端开源版展示从 300 改为 Infinity。

这样可以做到:
1. 后端功能上去除限制。
2. 前端显示与后端逻辑同步。
3. 改动最小，不扩散到无关模块。


============================================================
四、实际代码修改内容
============================================================

修改文件 1:
backend/domain/license.go

修改前:
  MaxNode                int   `json:"max_node"`                   // 单个知识库下文档数量
  MaxNode:  300,

修改后:
  MaxNode                int   `json:"max_node"`                   // 单个知识库下节点数量，0 表示不限
  MaxNode:  0,


修改文件 2:
backend/repo/pg/node.go

修改前:
  if count >= int64(req.MaxNode) {
      return domain.ErrMaxNodeLimitReached
  }

修改后:
  if req.MaxNode > 0 && count >= int64(req.MaxNode) {
      return domain.ErrMaxNodeLimitReached
  }


修改文件 3:
web/admin/src/constant/version.ts

修改前:
  docCountPerWiki: 300,

修改后:
  docCountPerWiki: Infinity,

九、部署机构建 API 镜像过程与故障排查
============================================================

构建命令:
  cd /data/pandawiki/custom-src/backend
  sudo docker build -f Dockerfile.api -t local/panda-wiki-api:remove-300 .

第一次构建耗时较长后失败，关键日志如下:

  => CANCELED [api 2/6] RUN apk update ... 1279.8s
  => ERROR [builder 4/6] RUN --mount=type=cache,target=/go/pkg/mod     go mod download 1261.9s

  go: github.com/chaitin/ModelKit/v2@v2.13.3: read "https://proxy.golang.org/github.com/chaitin/%21model%21kit/v2/@v/v2.13.3.zip": read tcp ...:443: read: connection timed out
  go: github.com/bytedance/sonic@v1.14.1: read "https://proxy.golang.org/github.com/bytedance/sonic/@v/v1.14.1.zip": read tcp ...:443: read: connection timed out
  ... (多个 go module 下载超时)

初步判断:
  Docker build 阶段的 go mod download 访问 proxy.golang.org 时连接超时。

进一步网络验证:

宿主机测试:
  curl -I https://github.com
  返回 HTTP/2 200

宿主机测试 proxy.golang.org:
  curl -I https://proxy.golang.org
  返回 HTTP/2 200

Docker 容器内测试 proxy.golang.org:
  sudo docker run --rm alpine:3.21 sh -c "apk add --no-cache curl >/dev/null && curl -I https://proxy.golang.org"
  返回 HTTP/2 200

结论:
  不是“完全无法访问外网”，而是 build 过程中大量模块下载时连接稳定性不足。

重试策略:
  使用宿主机网络执行构建:
    sudo docker build --network=host --progress=plain -f Dockerfile.api -t local/panda-wiki-api:remove-300 .

最终构建成功，结尾日志如下:

十、compose 修改与服务切换过程
============================================================

先检查 compose 中 api 段，最初发现仍然指向官方镜像:

  api:
    container_name: panda-wiki-api
    depends_on:
      - postgres
      - nats
      - caddy
      - raglite
    restart: always
    image: chaitin-registry.cn-hangzhou.cr.aliyuncs.com/chaitin/panda-wiki-api:v3.84.1
    volumes:
      - ./data/caddy/run:/app/run
      - ./data/nginx/ssl:/app/etc/nginx/ssl
      - ./data/conf/api:/data
    environment:
      - NATS_PASSWORD=${NATS_PASSWORD}
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
      - REDIS_PASSWORD=${REDIS_PASSWORD}
      - S3_SECRET_KEY=${S3_SECRET_KEY}
      - JWT_SECRET=${JWT_SECRET}
      - ADMIN_PASSWORD=${ADMIN_PASSWORD}
      - SUBNET_PREFIX=${SUBNET_PREFIX}
    networks:
      panda-wiki:
        ipv4_address: "${SUBNET_PREFIX:-169.254.15}.2"

说明:
  虽然本地镜像已经构建成功，但 compose 文件没改，所以运行中的容器依然是官方镜像。

用户还检查了 consumer 段:

  consumer:
    container_name: panda-wiki-consumer
    depends_on:
      - nats
      - api
      - raglite
    restart: always

    image: chaitin-registry.cn-hangzhou.cr.aliyuncs.com/chaitin/panda-wiki-consumer:v3.84.1
    environment:
      - NATS_PASSWORD=${NATS_PASSWORD}
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
      - REDIS_PASSWORD=${REDIS_PASSWORD}
      - S3_SECRET_KEY=${S3_SECRET_KEY}
      - JWT_SECRET=${JWT_SECRET}
      - SUBNET_PREFIX=${SUBNET_PREFIX}
    networks:
      panda-wiki:
        ipv4_address: "${SUBNET_PREFIX:-169.254.15}.3"

结论:
  consumer 配置是正常的，不需要改。

随后修改 api 段为:

  api:
    container_name: panda-wiki-api
    depends_on:
      - postgres
      - nats
      - caddy
      - raglite
    restart: always
    image: local/panda-wiki-api:remove-300
    volumes:
      - ./data/caddy/run:/app/run
      - ./data/nginx/ssl:/app/etc/nginx/ssl
      - ./data/conf/api:/data
    environment:
      - NATS_PASSWORD=${NATS_PASSWORD}
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
      - REDIS_PASSWORD=${REDIS_PASSWORD}
      - S3_SECRET_KEY=${S3_SECRET_KEY}
      - JWT_SECRET=${JWT_SECRET}
      - ADMIN_PASSWORD=${ADMIN_PASSWORD}
      - SUBNET_PREFIX=${SUBNET_PREFIX}
    networks:
      panda-wiki:
        ipv4_address: "${SUBNET_PREFIX:-169.254.15}.2"

然后执行强制重建 api 服务:
  cd /data/pandawiki
  docker compose up -d --force-recreate api
